## 1. 目的と判断の基準

今回作るのは、候補を生成し、固定した評価器で比較し、採用しない理由も含めて追跡できる研究の仕組みです。MVPの完了は、利益改善の実証とは区別します。合成データと固定応答で確認できるのは、データ契約、評価ロジック、台帳、権限の境界、停止と再実行が意図どおりに働くことです。

「自己改善」は、研究候補のパラメータと許可済み条件の組み合わせを更新することを指します。モデルの追加学習、稼働Botの自己書換え、自動リリースを意味しません。改善候補がなければ、候補を採用せず終了できることを成功条件に含めます。

本書は作業順序、依存関係、完了条件を管理します。権限と候補の許可範囲は正本、数値は `policy.json`、実装詳細は[技術書](TECHNICAL_DESIGN.md)、実行方法は[運用手順](OPERATIONS.md)を参照します。不一致があれば実験を停止して正本との整合を取り、別の文書に都合のよい例外を追加しません。

## 4. Phase 0：維持する仕様と回帰受入条件

### 4.1 契約を固定する

正本と `policy.json` を実験開始時に固定し、manifestへ版とhashを記録します。候補の数値範囲や合否基準を、CLIの別の既定値や生成プロンプトだけで重複管理しません。

MVPの候補生成は固定応答で、1実験の最大試行数は8です。不正JSON、重複候補、生成失敗も試行を消費します。実行時間、入力行数、JSONサイズ、保存量の上限はポリシーから適用します。

受入条件は、範囲外の値、未知の条件、必須条件の削除、重複キー、不正な数値、過大な入力が実行前に拒否されることです。候補は全てANDで結合する許可済みフィルタとパラメータからなり、Python、SQL、shell、URL、動的なプラグインを渡す経路を持ちません。

### 4.2 データを凍結し、評価を分離する

入力は凍結した5分OHLCVのCSVです。データとメタデータを検査してhashを記録し、指標準備区間の後を時間順にtrain、dev、holdoutへ分けます。ここでtrainは候補設計に利用できる過去区間を意味し、OpenAIモデルの追加学習を行うものではありません。

devでは連続した区間の成績と、時間順に3分割した各区間の独立した仮想口座による成績を確認します。3区間の利益を複利の連続運用として合算しません。この試験を、論文のCSCV実装や学習・再学習を含む完全なwalk-forward検証と呼びません。

全候補と固定比較戦略に同じ費用・執行・資金・データ境界を適用します。確定足から次の5分足で執行すること、上位足の参照時点、同じ足でSL/TPへ触れた場合の扱い、期間末の評価方法は正本と技術書に従います。研究候補のポジションも購入時にSL/TPを固定します。

受入条件は、欠損や未来参照を拒否し、同じ候補・データ・評価器から同じ成績を再計算できることです。5分OHLCVで再現できない足内順序・板厚・実滑りは、仮定としてレポートに表示します。合成データは常に合成と表示します。

### 4.3 選抜と最終評価の使用を制御する

候補生成器へ渡せる成績と最終評価を分け、holdoutを候補設計に使いません。devの固定基準を満たした最良の1件だけをholdoutへ進め、最終評価期間の使用を評価前に永続化します。中断・失敗しても使用予約を解除せず、同じ期間で次点候補を試し直しません。

合格は `REVIEW_REQUIRED` まで、合成データの結果は `DEMO_ONLY` とします。候補なし・不合格は正常な研究結果です。合格基準を実行中に緩める処理は設けません。台帳の作り直しでholdoutの使用履歴を回避しない運用を明示します。

最大8試行、devの3分割、holdoutの一度だけの使用は、誤った後選びを抑える本プロジェクトの制御です。これだけで過学習を除去した、統計的有意性を示した、将来利益を証明したとは主張しません。[R1][R2]

### 4.4 独立台帳とレポートを作る

研究専用SQLiteへ、実験manifest、試行予約、候補、検証結果、評価、holdout使用予約、状態遷移、終了理由を保存します。既存DBの接続設定を読み込まないこと、研究の保存先が既存DBや稼働領域と同じにならないことを確認します。

候補生成前に試行を予約し、生成済みの候補を保存してから評価します。再開時には正本・ポリシー・データ・評価器などのmanifest一致を確認します。同じ試行番号で別の候補を生成し直して成功扱いにすることはありません。状態更新と監査イベントを同じトランザクションで扱い、書込み失敗や整合性不明を成功へ変換しません。

HTMLレポートには、比較基準、データの種別と期間、全試行数、候補別の採否理由、費用仮定、devとholdoutの区別、再現に必要なhash、残る限界を表示します。秘密や外部の生エラー本文を出力せず、候補名などをHTMLとして実行できない形で表示します。

### 4.5 Responses契約を固定応答で確認する

将来利用するResponses APIのリクエスト生成と応答解析を用意し、fixture transportだけで試験します。APIキー、外部通信、OpenAI SDKによる実リクエストは不要です。CLIから本番providerを指定した場合は拒否し、エラー時に実providerへ切り替わるfallbackを設けません。

検証には、正常な構造化出力、拒否、不完全応答、欠落した本文、未知の項目、不正JSON、過大出力を含めます。Structured Outputsを使う将来の接続でも、ローカル検証と決定論的な採点は省略しません。[R3][R4][R5]

### 4.6 検収する

MVPの過去検収は[2026-11-05の記録](ACCEPTANCE_20261105.md)へ残し、今回の回帰検証は[Phase 2検収書](ACCEPTANCE_PHASE2_20261106.md)へ対象SHA付きで記録します。未実行の項目を、計画書に書かれていることだけで合格としません。

- 合成データ・固定応答で、生成、検証、評価、採否、台帳、HTMLレポートまで完結する。
- 上限到達、不正候補、重複、改善候補なしでも有限時間で終了する。
- 予約前後・候補保存後・評価途中の中断、再実行、同時起動を検証し、二重計上やholdout再利用がない。
- データ・ポリシー・正本・評価器の変更を伴う再開を拒否する。
- JSONの型・範囲、未来参照、同時SL/TP、固定比較戦略との一致など、結果へ影響する境界を検証する。
- 不正provider、実API、既存DB、稼働Compose、任意コードへの到達経路がないことを確認する。
- 既存戦略・資金・決済・DB権限・認証の意図しない変更がないことを確認する。診断修正の差分と、稼働環境へ未反映であることを区別する。

今回の検収結果が示すのは仕組みの動作と境界です。実データでの改善率、期待利益、勝率、将来の収益性は未検証と表示します。

## 5. Phase 1：実データと独立paper比較

Phase 1では、データを入れ替えるだけで実戦性能の証拠が得られると考えず、取得時点を含めたデータ品質と、評価器の実行仮定を検証します。

まず、提供元、BTC/JPYの市場、UTC時刻、取得時刻、訂正履歴、欠損区間、確定時刻を保存します。後から修正されたデータを当時既知だったものとして使わず、各判断時点で参照できた範囲を復元します。入力元が別取引所なら、その事実とCoincheckへの適用限界を表示します。

比較戦略と候補を同一の凍結データで評価した後、独立した仮想口座で将来到着するデータを使って並行比較します。現行 `baseline` と `news_gate` の口座、残高、約定を比較用口座へ流用しません。実データの不足、決済件数不足、費用条件の不確かさがあれば、良さそうな損益が出ても「判断保留」とします。

研究頻度は5分ごとの市場確認や2時間足の確定とは別に定めます。疎な2時間足の取引では、毎日切り替えるだけの新しい証拠が増えない場合があります。十分な新規データと決済件数、前回研究からの冷却期間、累積試行数を満たしてから次の研究を開始する方針とし、具体的な頻度はこの段階の観測結果から事前に決めます。成績を見てから頻度や基準を変更した場合は、新しい研究系列として記録します。

同じデータに対する実験IDの作り直しでも探索回数は増えます。Phase 1では実験をまたぐデータ系列・仮説系列の履歴を集約し、最良候補だけでなく累積の試行数と失敗も判断資料に含めます。[R1]

ニュース実験は、記事本文、公開時刻、取得時刻、当時の分類結果を復元できるpoint-in-time corpusが用意できるまで行いません。現在の検索結果や後日更新された記事を過去へ差し戻して成績を算出することは認めません。

Phase 1の完了条件は、未使用期間と前向き比較から、採用候補があるか、改善の根拠が足りないかを説明できることです。特定の利益額や経過日数の達成を必須の結論にしません。[R2]

## 6. Phase 2：今回完成させるコードと検収

### 6.1 1候補の閉じた経路

`prepare-proposal` が凍結CSVから要求書を作り、別プロセスの生成器が候補を保存し、`evaluate-artifact` が同じCSV・分割・予算・policy・コードから要求書を再構築して照合します。評価の試行数は1固定です。要求書の中身を信じて入力データの照合を省略しません。

モデルへ送るcontextは学習統計と許可された開発フィードバックだけです。本版の単一候補フローではtrial 0、開発フィードバックは空です。最終評価の値・成績、既存の口座情報、秘密を渡しません。改善を繰り返す多段の実AIループは、外部候補待ちの状態・累積予算・重複期間を設計してからの拡張です。

候補はDSL検証の後に評価します。任意providerを注入せず、既存fixtureか、検証済み成果物を読む固定実装だけを許可します。生成元がfixtureなら、モデル名が記録されていても実API使用と表示しません。

### 6.2 費用・秘密・通信

固定モデル、料金版、上限と有効期限の数値は`phase2_policy.py`を正本とします。本版は`gpt-4.1-2025-04-14`の全コンテキスト上限と最大出力2,048tokenから、1回につき2,111,536 microUSDを保守的に予約します。呼出側が小さい見積額を指定する入口は設けません。価格・計算・停止予定の根拠は正本10節に記載します。[R6][R7]

上限は明示初期化時に固定します。金額は1回・UTC日次・累積、回数はUTC日次・累積です。各呼出しを永続台帳へ原子的に予約し、失敗・timeout・送信後crashも枠を消費します。過去日の未確定・失敗予約と、過去日の予約が当日完了した分は、当日の露出へ満額で持ち越します。成功時にも予約との差額は戻しません。usageから計算する金額は実請求の確認とは別です。fixtureで計算するusageと費用は模擬値です。

fixtureとliveは別stateを使います。通常の評価器はキーもネットワークも持たず、liveだけが専用キーfileを読み、固定HTTPS宛先へ送信します。キーや予算の未設定を回避するため、既存newsや他プロジェクトの秘密を流用しません。[R4]

一つの永続volumeを保持する運用が前提です。別台帳や別プロジェクトから同じキーを使用することまで集計する仕組みではなく、管理者によるファイル削除や提供者側の料金変更まで防ぐ請求保証でもありません。料金版と期限はレビューして更新し、履歴を消して上限を補充しません。

### 6.3 受入項目

| 項目 | 必要な証拠 |
|---|---|
| opt-in・キー・安全フラグ | 不足・不正時は送信0回。fixtureはキー不要、実HTTPなし |
| 予約 | 複数プロセスの競合でも金額・回数上限内。日付変更と再起動で累積枠を補充しない |
| 不正な予算 | 型・範囲・過小予約・初期化後の増額・別料金版・期限切れを拒否 |
| 異常応答 | HTTP失敗、timeout、拒否、不完全出力、重複JSONキー、モデル・usage不整合を拒否 |
| 再実行 | 同要求を二重送信しない。未確定や成果物欠損を新規通信で補わない |
| 成果物 | schema、候補、全hashと束縛、サイズ、symlink、差し替えを検査 |
| 評価 | 保存候補から研究台帳・比較・レポートまで到達。holdout非開示、同run再開の不変性 |
| 権限 | generatorに注文・Bot DB・Docker・Git権限なし。評価器はnetworkなし・秘密なし |
| 秘密 | CLI、例外、HTTP失敗、ログ、成果物へキー等を出さない |
| 表示 | fixture/live、上流生成試行、評価器の通信0、使用価格版・予約額・usage換算を区別 |

本版のコードmerge条件は、必要なfixture・回帰・分離試験と必須CI、独立レビューです。実API未検証の場合、既定無効として統合できる範囲を明示します。実API互換性、実請求、候補品質、利益改善は別の検収項目として残します。

### 6.4 実API有効化前の残件

対象プロジェクトでのモデル利用可否、専用キーの注入とUID、有限上限、対象コードSHAを確認します。既承認の接続方針を理由に無制限の費用や別用途のキー利用を許可したとは扱いません。

モデルは2027-01-14停止予定です。料金ポリシーは2026-12-06 00:00 UTCに先に失効し、以降の新規live予約を拒否します。モデル更新は料金、schema、usage、fixture、拒否・費用試験をまとめたレビュー済み変更にします。実応答は保存した候補本体を再評価し、モデル名・seedだけから完全再現できるとはしません。[R3][R5][R7]

## 7. Phase 3：限定的なpaper自動反映

この段階で初めて、事前にレビューされた範囲で候補のpaper反映を検討します。対象は仮想口座だけで、昇格条件、必要な標本数、冷却期間、同時評価数、停止条件、反映記録、巻戻し先を実装前に固定します。

候補を反映する場合は、新規ポジションに新しい戦略版を割り当てます。保有中のポジションは購入時の戦略版、ATR、固定SL/TPで管理します。巻戻しでも履歴を書き換えず、損失を消すために仮想残高や台帳を初期化しません。

導入前に、切替時の未処理シグナル、同時起動、再起動、約定待ち、既存ポジションの終了、旧版への復帰を試験します。稼働対象SHAを確認した上で別途反映し、GitHub `main` の更新とiMac・VPSの稼働更新を混同しません。

昇格は日数だけで判断しません。比較対象を超える根拠が不足している、データが不健全、費用や挙動の差が説明できない場合は、現状維持と研究停止を選べる設計にします。

## 8. Phase 4：レビュー可能なコード変更案

新しい指標やロジックを任意コードとして提案する場合は、許可されたパスへの差分を別ブランチへ出すところから始めます。生成されたPythonをMVPのJSON評価器に渡して実行する拡張は行いません。

任意コードの評価には、秘密を持たない別sandbox、ネットワーク制限、読み取り専用の入力、CPU・メモリ・プロセス数・ディスク・実行時間の上限、依存追加の審査を設計します。Docker socketやホスト管理権限を渡さず、生成器と実行環境を分離します。通常のコンテナを使ったことだけを、敵対的コードの隔離を保証した根拠にはしません。

レビュー用の差分、静的検査、意味のある回帰試験、基準戦略との差、再現可能な実行記録を揃え、人が確認した固定SHAだけをリリース候補にします。JSON DSLの制約下で安全だった実績を、任意コードの自動実行・自動マージの承認へ転用しません。[R4]

## 9. 共通の停止条件と残るリスク

| 検出した状態 | 処理と次の判断 |
|---|---|
| データ欠損、未確定足、不正OHLC、時刻の不整合 | 評価を開始しない。データを修復した場合は新しいhashと実験として扱う |
| 正本・ポリシー・データ・評価器のhash不一致 | 再開を拒否し、どの契約が変わったか確認する |
| 台帳の破損、書込み失敗、二重予約、保存量超過 | 研究を停止する。履歴の削除や別台帳への逃避で継続しない |
| 試行数・時間・入力量・費用の上限到達 | 未完了の状態と理由を記録し、新しい候補生成や通信を止める |
| holdoutの既使用、生成器への露出、候補選抜への混入 | 当該研究の最終評価を有効な未使用検証として扱わない |
| 基準未達、標本不足、費用ストレスで優位性消失 | 不採用または判断保留として終了する。基準を後から下げない |
| 評価器・fixtureへの実provider/秘密の混入、生成器から注文・Bot DB・任意コードへの到達 | 境界逸脱として実行を停止し、原因修正と再検証を行う |
| HTMLやログへ不信頼文字列が未処理で入る | レポート生成を修正し、実行される本文や秘密の露出を防ぐ |

研究停止は既存ポジションの強制売却を意味しません。既存Botの損切り・利確、DB、稼働サービスへ研究停止の副作用を伝えません。

残るリスクには、少数取引による推定の不確かさ、同じデータへの適応、別市場や別相場への性能劣化、実滑りの再現不足、履歴を管理者が破棄できること、将来モデルの挙動変化があります。これらを「AIが選んだ」「基準を通過した」「hashが一致した」という理由だけで解消済みとしません。

## 10. 根拠資料とこの計画への適用

[R1]〜[R5]はMVPの2026-11-05版から継承した一次資料、[R6]・[R7]は2026-11-06に確認したAPI仕様・料金・廃止予定です。外部資料は設計上の考え方を支えるもので、本プロジェクトの候補数、閾値、利益、成功率を保証しません。Agent Builderに関する資料は不信頼入力と権限分離の原則を参照しており、同製品の採用を計画しているわけではありません。

- **[R1] Bailey, Borwein, López de Prado, Zhu (2015), The Probability of Backtest Overfitting.** [著者公開論文](https://www.davidhbailey.com/dhbpapers/backtest-prob.pdf)。多数の試行からの選択とバックテスト過学習を扱い、試行数を無視したholdout判断の限界を指摘する。本計画では全試行の保持、有限な探索、最終期間の保護へ反映する。論文のCSCVやPBO推定はMVPで実装したとは主張しない。
- **[R2] Cerqueira, Torgo, Mozetič (2020), Evaluating time series forecasting models: an empirical study on performance estimation methods, Machine Learning 109, 1997–2028.** [著者所属機関の論文](https://kt.ijs.si/igor_mozetic/papers/CerTorMoz-TimeSer-MACH-20.pdf)、[DOI](https://doi.org/10.1007/s10994-020-05910-7)。時系列の性能推定法を比較し、非定常系列では時間順の複数期間によるout-of-sample評価が良い推定を示した。全ての時系列で同じ方法が最良という主張ではない。本計画では時間順の分離と独立した将来データ比較へ適用する。
- **[R3] OpenAI, Evaluation best practices.** [公式資料](https://developers.openai.com/api/docs/guides/evaluation-best-practices)。目的・データ・指標を定義し、変更ごとの評価と人による確認を行う。本計画ではDSLの契約、採点、停止条件、生成器の継続評価を具体的な検査対象にする。
- **[R4] OpenAI, Safety in building agents.** [公式資料](https://developers.openai.com/api/docs/guides/agent-builder-safety)。不信頼本文を高優先の命令へ昇格させず、構造化フィールドと権限の制限でリスクを抑える。本計画では記事・AI出力から注文、秘密、デプロイへ到達する経路を与えない。
- **[R5] OpenAI, Structured model outputs.** [公式資料](https://developers.openai.com/api/docs/guides/structured-outputs)。構造化出力でも拒否や不完全応答を個別に扱う必要がある。本計画ではfixtureによる異常系試験、ローカル再検証、独立した成績計算を維持する。
- **[R6] OpenAI, GPT-4.1 / Pricing.** [固定モデルの公式仕様](https://developers.openai.com/api/docs/models/gpt-4.1)、[公式価格表](https://developers.openai.com/api/docs/pricing)。本版の固定単価・コンテキスト上限の根拠。月額支出や実請求額の保証には使わない。
- **[R7] OpenAI, Deprecations.** [公式廃止予定](https://developers.openai.com/api/docs/deprecations)。GPT-4.1の2027-01-14停止予定をモデル更新期限の根拠として扱う。
