## 1. この文書の役割

本書はAI自己改善エンジンの**目的、権限、変更可能範囲、検証方法、段階的な拡張条件**を定める正本です。
計画書、技術書、実行手順、生成されたレポートは本書を参照します。
生成AIの説明、過去のチャット、実験結果を理由に、実装が本書の権限を拡大してはいけません。

数値の実行上の定義は [`ai_lab/policy.json`](../../ai_lab/policy.json) に一元化し、型・範囲・候補JSON Schemaはそこから構築します。
本書と実装の不一致は不具合です。都合のよい方を自動採用せず、変更差分と試験結果を残して版を更新します。
同じ実験の再開時に、正本・ポリシー・データ・評価器のhashが変わっていた場合は再開を拒否します。

参照文書： [計画書](PLAN.md) / [技術書](TECHNICAL_DESIGN.md) / [運用手順](OPERATIONS.md) / [今回の検収書](ACCEPTANCE_20261105.md)。

## 2. 目的と「自己改善」の意味

市場環境の変化や蓄積した研究結果を入力に、システムが次の候補を作り、同じ評価器で比較し、改善の根拠と不採用理由を保存します。
本MVPが更新するのは**研究候補のパラメータと、あらかじめ実装された条件の組み合わせ**です。
OpenAIモデル自体の重みを追加学習する機能ではありません。

成功は「必ず利益の増える戦略を見つけたこと」ではありません。
**再現可能な試行、検証データへの不正な最適化の抑制、権限逸脱の防止、改善がない場合に現状を維持する判断**ができることを、MVPの成功と定義します。
利益改善は、実データでの独立検証と、その後に到着するデータでの比較運用によって別途評価します。

## 3. 既存Botとの関係

既存Botの稼働コード、仮想残高、約定、収集データ、DB権限、稼働中Composeを研究エンジンから変更しません。
新しい研究用SQLite台帳と専用出力領域を使用し、既存PostgreSQLへ接続しません。
将来PostgreSQLへ研究台帳を移す場合も、別DB・別ロール・別migrationで扱います。

固定比較戦略は以下です。実装上の一致は既存 `app/strategy.py` と比較して確認します。

| 項目 | 固定比較戦略 |
|---|---|
| 決定足 | 確定2時間足 |
| ローカル条件 | 終値 > EMA21 > EMA55、EMA55が3本前より上昇 |
| RSI | Wilder RSI9、55上抜け。クロス足＋次の3本、判定時も55以上 |
| 上位足 | 判定時点で確定済みの4時間足、終値 > EMA50 > EMA200 |
| 指標の参照履歴 | 各足の直近最大450本。準備にローカル200本・上位300本を要求 |
| ATR | Wilder ATR14、シグナル時の値を約定時に固定 |
| 損切り / 利確 | 約定価格から3 ATR下 / 12 ATR上 |
| 保有 | ロングのみ、1仮想口座1ポジション、買い増しなし |
| 重複防止 | 同一RSIクロスイベントからの再購入を禁止 |

`baseline` と `news_gate` の現行仮想口座は独立したままです。
研究の各評価も独立した仮想資金から開始し、既存口座や他候補から損益を移しません。

## 4. 必須の安全境界

以下の条件は候補JSONやAI出力では変更できません。

1. `DRY_RUN=true`、`LIVE_TRADING_ENABLED=false`、`NEWS_MODE=mock`。
2. 1回の仮想購入による現金支出は手数料込みで最大50,000円。13,000円等へ下げる設定も有効。
3. 評価用初期仮想資金は100,000円。購入上限とは別の概念であり、既存残高を初期化しない。
4. 実注文、Coincheck private API、送金、秘密鍵取得を実装・実行しない。
5. MVPの生成器は固定応答。実OpenAI通信、有料ニュース、Web検索、外部URL取得を実行しない。
6. 本MVPはOpenAI秘密を必要としない。既存news専用資格情報を研究プロセスへ流用しない。
7. 任意Python、`eval`、`exec`、動的プラグイン、シェル、Git操作、Docker操作を候補に許可しない。
8. 合格基準、データ分割、資金制約、手数料、試行上限をAIが変更できない。
9. 研究の合格によって稼働Botへのリリースや既存ポジションのSL/TP更新を行わない。
10. 研究中の障害は研究の停止で処理し、全売却・DB初期化・volume削除へ結び付けない。

これらは注意書きだけでなく、設定拒否、許可するJSON項目、通信不能なDocker設定、保存領域の分離、受入試験によって確認します。

## 5. MVPで候補が変更できるもの

以下は**研究候補だけ**に適用します。固定比較戦略や稼働設定を書き換えるものではありません。

| 候補項目 | 許可範囲 |
|---|---|
| 時間足 | 30分、60分、120分 |
| EMA | fast 9〜50、slow 21〜100、fast < slow |
| RSI期間 | 9、14 |
| RSI上抜け閾値 | 45、50、55、60 |
| クロス有効期間 | クロス足＋0〜3本 |
| ATR期間 | 14、28 |
| ATR損切り倍率 | 1.5、2、3、4 |
| ATR利確倍率 | 3、6、9、12 |
| 必須条件 | local_trend、higher_trend、rsi_cross |
| 追加条件 | slow_rising、volatility_cap |
| volatility_cap | ATR / 終値 × 100 の上限0.5〜10% |

条件は全てANDで結合します。未知条件、重複条件、必須条件の削除、未定義のコードやURLを含むJSONは拒否します。
条件名の組み合わせによる変更もロジック変更として保存します。
MVPでは上位4時間足EMA50/200、決済方式、保有数、資金、約定ルールは固定です。
新しい指標を追加する場合は、人が実装とテストをレビューした上でDSLと正本を更新します。

5分・15分足を候補範囲へ追加することは将来の拡張です。5分OHLCVを入力にすることと、5分戦略を研究対象にすることは区別します。

## 6. データ契約

- 入力は凍結した5分OHLCV。UTCの足開始時刻、OHLC、出来高を持ちます。
- NaN、Infinity、価格0以下、不正OHLC、負の出来高、重複、欠損、順序違反、5分境界違反、未確定足を拒否します。
- 約定がなかった時間と、収集できなかった時間を混同しません。欠損を前値で補間して正常な足とみなしません。
- MVPはデータhash、自己申告の提供元、足の期間、利用可能時刻の仮定を記録します。提供元の自己申告は真正性の証明ではありません。
- BTC/JPYの入力であることは利用者が確認する前提です。ペアの機械検証、収集時刻・訂正履歴の管理、`--as-of` のmanifest保存はMVPでは未実装です。実験開始時刻を収集時刻の代わりにしません。これらは実データ検証へ進むPhase 1の要件です。
- 合成データは全画面・レポートで合成と明示し、運用成績として表示しません。
- bitbank等の他取引所のデータをCoincheck実約定として表示しません。
- 過去のニュースを将来情報なしに再現できる記事・取得時刻の履歴がない限り、ニュース改善の成績検証は実施しません。

50日分を指標準備のため確保し、その後を時間順に学習、開発、最終評価へ分けます。
最終評価区間は候補生成器へ渡しません。評価器のインジケーター計算に使える過去と、候補選択へ開示する成績を区別します。

## 7. 評価契約

売買条件は確定足で決定し、その後の最初の5分足始値を執行価格の基準とします。
判定に使用した終値で必ず売買できたものとして計算しません。
上位足は決定時点までに終了しているものだけを使用します。

購入数量は手数料込み予算からBTC小数点8桁へ切り下げ、0.001 BTC / 500円の研究用注文制約を適用します。
最小注文を満たさない場合はスキップし、予算を増額しません。
これらの注文制約は既存Botから継承するシミュレーション条件であり、本MVPで取引所への実注文検証を行ったという意味ではありません。

ポジションのSL/TPは購入時に固定します。ギャップ時は損切り指定価格での約定を保証せず、同じ5分足でSLとTPに触れた場合は損切り優先で評価します。
5分OHLCVでは足内の正確な順序、板厚、実際の滑りを再現できないため、このルールの限界を成績に併記します。

費用の初期仮定は片道手数料0 bps、往復スプレッド5 bps、片道滑り10 bpsです。
これらはCoincheckの実測値ではありません。費用2倍のストレス試験も同条件で行います。

全開発区間の連続シミュレーションと、その区間を3分割して各区間を独立資金から評価する試験を行います。
分割試験の損益を連続複利運用の損益として合算しません。
評価期間末の決済を、実戦略が売りシグナルを出したこととして扱いません。
通常の決済には最小数量・最小金額も適用します。最小金額を満たさない売却は保有を継続し、拒否回数を記録します。
期間末は比較用の費用控除後評価を別に計算し、注文制約を満たす実際の売却を保証しません。通常決済件数・勝率・PF・実現損益からこの評価用清算を除き、期間末評価損益として別記します。

## 8. 候補選抜と最終確認

次の初期基準は研究用の固定ルールです。最適値・統計的有意性・利益の保証を意味しません。

| 判定項目 | 初期基準 |
|---|---|
| 通常決済件数 | 20件以上。期間末の評価用清算は除外 |
| 費用込み利益 | 0円より大きい |
| 固定比較戦略との差 | 同じ区間で0円より大きい |
| 最大ドローダウン | 10%以下 |
| 最大1件の利益寄与 | 正の損益の合計に対して50%以下。期間末の評価益も含めて検査 |
| 開発区間の分割 | 3区間中2区間以上が利益正 |
| 費用ストレス | 費用2倍でも利益正・固定戦略を上回る |

条件を満たした候補のうち、開発区間の費用込み純利益が最大の1件だけを最終評価に進めます。
同点は候補hashの順で決め、手作業の後選びを避けます。
基準を満たした候補がなければ「改善候補なし」で正常終了します。

最終評価区間の予約を実行前に永続化します。失敗や中断があってもその期間を未使用へ戻しません。
同じ台帳で重なる最終評価期間の再利用を拒否します。
最終評価の不合格を見て、次点候補を同じ期間へ順に投入することは認めません。

合格は `REVIEW_REQUIRED` までです。合成データなら `DEMO_ONLY` として扱います。
MVPには `DEPLOYED`、`LIVE`、自動資金配分の遷移がありません。
新しい台帳を作れば制約を回避できるため、台帳を保持する運用も必須です。ローカル管理者による履歴破棄まで技術的に防ぐものではありません。

## 9. 有限の試行と記録

1実験の候補生成は最大8回。上限は開始時に固定し、不正出力、重複、失敗も消費に含めます。
候補の生成前に試行を予約し、候補・結果・状態変更を台帳に記録します。
途中停止後に、予約済みの同じ試行へ別候補を生成し直してはいけません。
生成済み候補の評価再開は、実験manifestの一致を確認して行います。

記録には正本版/hash、ポリシーhash、データhash、評価器ソースhash、Python版、候補JSON/hash、生成器とプロンプト識別子、使用した費用と予算、分割期間、採否理由を含めます。
ログやレポートへ秘密、口座識別情報、AIの生のエラー本文を保存しません。
監査イベントはアプリから追記のみとし、状態更新と同じトランザクションで保存します。
hash連鎖は整合確認用であり、ホスト管理者による全面改変を防ぐ署名ではありません。

## 10. OpenAI APIとの境界

MVPはResponses API用の構造化リクエストと応答パーサーを用意し、固定応答で契約試験を行います。
Structured Outputsは出力形式の制約であり、利益・事実・安全性の保証ではありません。
出力はローカルでも型、範囲、項目、サイズを再検証し、拒否・不完全応答・不明な項目は候補に採用しません。

実APIとの接続は次段階です。許可するモデルとスナップショット、入力情報、1試行の上限、日次費用、失敗時の予算消費、通信権限、秘密の保持先を別途確定します。
現在のnews専用秘密方針を黙って変更しません。必要なら専用の制限付き生成サービスを追加し、研究評価器へ秘密やネットワーク権限を与えない構成をレビューします。

将来でも、記事本文・AI出力を権限ある命令として扱いません。
外部本文からデプロイ・注文・秘密参照へ到達するツールは与えません。

## 11. 将来の自動反映

実データでの過去検証に続いて、現行戦略と候補を独立仮想口座で並行稼働させ、未使用の将来データで比較します。
十分な決済数、データ品質、費用、稼働安定性を満たしてから、別にレビューされた変更として限定的なpaper反映を検討します。
日数だけで自動昇格しません。新しい戦略は新規ポジションにだけ適用し、既存ポジションは購入時の戦略版と固定SL/TPで管理します。

コード生成へ拡張する場合は、許可範囲を絞った別ブランチへの差分提案とします。
任意Pythonの隔離評価、依存追加、CPU/メモリ制限、秘密遮断、レビュー、CI、固定リリースを新たに設計します。
JSON候補の安全性を、任意Pythonを実行してよい根拠に転用しません。

## 12. 正本の更新手続き

1. 変更理由・影響する規則・既存ポジションへの扱いを差分で示す。
2. 必要ならpolicy/schema版を上げ、旧実験は旧manifestのまま残す。
3. 変更点に対応したテストを追加し、既存Botの不変性も確認する。
4. 計画書・技術書・手順・検収書との不一致を解消する。
5. 改修ブランチへcommit/pushし、固定SHAをリリース候補とする。
6. 稼働環境への反映は別の承認・実施・検証として記録する。

AIが提案文や実験結果を生成しただけでは、本書の規則は変更されません。
